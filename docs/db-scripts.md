# สคริปต์ DB

> อ่านอย่างเดียวต้องพิสูจน์ด้วยเทส · เขียนต้อง dry-run ก่อน · ใช้ได้กับ DB ทุกชนิด
> สถานะ: v0.3.0 (2026-11-21)

หลักการ: สคริปต์ที่แตะ DB จริงเป็นความเสี่ยงสูง · agent เขียนและทดสอบได้ แต่การรันบน prod ต้องมีคนอนุมัติ ผูกกับไฟล์ที่ตรวจแล้ว · ใช้ skill `db-script`

## อ่าน vs เขียน — แยกกันเสมอ
| ชนิด | ตัวอย่าง | อนุมัติ |
|---|---|---|
| read | สำรวจ · นับ · ตรวจข้อมูล | การอนุมัติอ่านข้อมูลจริงที่ผูกกับ hash ของสคริปต์ (บน prod) |
| write | เพิ่ม / แก้ / ลบ / backfill / migration | ใบขอ deploy (R2/R3) + backup + แผนถอย |
- หนึ่งไฟล์ทำอย่างเดียว · ห้ามผสมอ่านกับเขียน
- DB role แยก: สคริปต์อ่านใช้บัญชีที่มีสิทธิ์อ่านอย่างเดียว (ไม่ใช่แค่สัญญาว่าไม่เขียน)

## โครงโฟลเดอร์
กรอกต่อโปรเจกต์: ปรับชื่อได้ แต่ต้องแยกอ่าน/เขียนและมีเทสอยู่ข้างกัน
```
scripts/db/
  read/        <date>-<purpose>.*  + เทส
  write/       <date>-<purpose>.*  + เทส
  migrations/  NNNN-<name>.*  (+ แผนถอย)
```
- ตั้งชื่อ: วันที่ + จุดประสงค์ · หนึ่งการ์ดอ้างหนึ่งสคริปต์

## การต่อ DB
- รับ connection จาก environment variable (12-Factor) ที่ตัวรันตั้งให้ · ไม่โหลด `.env` เอง ไม่อ่านไฟล์ secret ในสคริปต์
- ไม่ฝัง URI/รหัสในโค้ดหรือเทส · เทสใช้ DB ทดสอบ/container ชั่วคราว
- ตรวจ "ชื่อ DB ที่ต่ออยู่ตรงกับที่คาด" ก่อนทำอะไร (เทียบทั้งชื่อ) ไม่ตรง = ออกทันที

## กันโหลด (สคริปต์อ่าน)
- เลือกเฉพาะ field ที่ต้องใช้ · ไม่ดึงทั้งระเบียน
- จำกัดจำนวนผลลัพธ์ · ตั้ง timeout ต่อ query และเวลารวมของสคริปต์
- ดูแผนการรัน (query plan) ว่าใช้ index ก่อนส่งตรวจ · ข้อมูลใหญ่แบ่งอ่านเป็นช่วง
- รันนอกช่วงทราฟฟิกสูง หรือใช้ replica ถ้ามี

## ห้ามเดาค่า
- ก่อนกรองด้วยค่าสถานะ ดูค่าที่มีจริงในข้อมูล ไม่เดาจากชื่อ
- ตั้งสมมติฐานเป็นข้อ ๆ ให้ผลสคริปต์ยืนยัน · ไม่ชัด = เขียน "ยังไม่ได้ตรวจ"

## ผลและ exit code
- ใช้แบบสากล: `0` = สำเร็จ · ไม่ใช่ `0` = ไม่สำเร็จ · ความหมายย่อยเขียนไว้ในหัวสคริปต์
- ตรวจไม่สำเร็จ (ต่อไม่ได้ · หมดเวลา · ข้อมูลไม่พอ) = จบด้วยค่าที่ไม่ใช่ `0` และแยกให้ชัดจาก "ตรวจแล้วไม่พบ"
- ข้อความ error ไป stderr · บรรทัดท้ายสรุปผลให้คนอ่านเข้าใจ

## ไม่หลุด (PII และ secret)
- ผลลัพธ์/log พิมพ์เฉพาะจำนวน รหัส error และสถิติรวม · ไม่พิมพ์ id รายคน อีเมล เบอร์ ค่า secret
- ต้องดูตัวอย่าง = ปิดบังบางส่วน และผ่าน GATE-PRIVACY
- ข้อความ error ไม่รวม connection string

## เทสบังคับ
- สคริปต์อ่าน: เทสพิสูจน์ว่าไม่เขียน (รันด้วยบัญชีอ่านอย่างเดียว หรือเทียบข้อมูลก่อน/หลัง)
- ข้อมูลที่รู้คำตอบ: ใส่ชุดตัวอย่างแล้วต้องได้ผลตามนั้น
- ทดสอบกับ DB ชนิดเดียวกับ prod (ไม่ใช่ mock ล้วน)
- เคสผิดพลาด: ชื่อ DB ไม่ตรง · หมดเวลา · ผลว่าง → exit code และข้อความถูกต้อง
- เขียนเทสก่อนสคริปต์ (TDD)

## ขออ่านข้อมูลจริง
Checklist ก่อนขอ (คนตรวจ · กรอกต่อโปรเจกต์: คำสั่งตรวจของโปรเจกต์ ถ้ามี):
- [ ] อ่านอย่างเดียว · ใช้บัญชีอ่านอย่างเดียว · ตรวจชื่อ DB
- [ ] จำกัดผลลัพธ์ + timeout · ไม่ดึงข้อมูลส่วนบุคคลเกินจำเป็น
- [ ] เทสผ่าน · ลองบน UAT หรือข้อมูลทดสอบแล้ว (แนบผล)

ขั้นตอน:
1. `prod-reader` (หรือ Dev) เตรียมสคริปต์ → ไล่ checklist → คำนวณ sha256 ของไฟล์
2. โพสต์ `templates/db-read-approval-request.md` บนการ์ด: path + sha256 + commit · วัตถุประสงค์ · ข้อมูลที่จะอ่าน · ผลเทส
3. Ops (หรือผู้ที่ทีมกำหนด) อนุมัติเป็นความเห็นที่ระบุ sha256 + บทบาท + วันที่ · ตัวอย่างข้อความ (ปรับต่อโปรเจกต์ได้): `DATA-ACCESS-APPROVED <sha256>`
4. `prod-reader` หรือ Ops รัน **หลังได้อนุมัติเท่านั้น** · เทียบ sha256 ก่อนรัน · ไฟล์เปลี่ยน = ขอใหม่
5. โพสต์ผลสรุปกลับบนการ์ดพร้อมที่มา

## สคริปต์เขียน
- **dry-run เป็นค่าเริ่มต้น:** แสดงว่าจะเปลี่ยนอะไร กี่ระเบียน โดยไม่เขียน · ต้องใส่ flag ชัดเจน (เช่น `--apply`) จึงเขียนจริง
- **ตรวจชื่อ DB** ก่อนเขียน ไม่ตรงหยุด
- **allowlist:** ระบุชุดข้อมูลและเงื่อนไขที่แก้ได้ · นอกรายการ = ปฏิเสธ · ไม่มีคำสั่งแก้/ลบที่ไม่มีเงื่อนไข
- **backup ก่อน apply** ตรวจว่ากู้ได้ และเก็บเลขอ้างอิง backup บนการ์ด
- **แผนถอยก่อน apply:** สคริปต์ย้อนผลหรือ restore · ทดสอบบน UAT/ข้อมูลทดสอบแล้ว
- ทำเป็นชุดเล็ก (batch) + idempotent (รันซ้ำไม่เสียหาย) + นับก่อน/หลัง
- ตรวจผลหลัง apply ด้วยสคริปต์อ่าน · ทุกอย่างผ่านใบขอ deploy

## Migrations
- Forward-only: ไม่แก้ migration ที่ขึ้น prod แล้ว · แก้ด้วย migration ใหม่
- ทุก migration มี "แผนถอย" ระบุไว้ (ย้อนผลหรือ restore) แม้ไม่ได้เขียนเป็นโค้ด down
- ใช้ expand/contract: เพิ่มของใหม่ (compatible) → ย้ายข้อมูล → ย้ายโค้ด → ลบของเก่าเป็นรอบแยก
- migration ที่ล็อกข้อมูลนานหรือย้อนไม่ได้ = R3
- ทดสอบบน UAT ด้วยข้อมูลปริมาณใกล้จริง และวัดเวลา

## ข้อมูลส่วนบุคคล (GATE-PRIVACY)
เปิด gate เมื่อสคริปต์/ฟีเจอร์แตะข้อมูลส่วนบุคคล (security-engineer ตรวจ):
- มี data inventory: เก็บอะไร · เพื่ออะไร (purpose) · เก็บนานเท่าไร (retention) · ใครเข้าถึง
- เก็บเท่าที่จำเป็น (minimisation) · ปิดบัง/เข้ารหัสตามความอ่อนไหว
- ไม่คัดลอก PII ออกจาก prod ไปที่อื่นโดยไม่ anonymize
- ลบ/ส่งออกข้อมูลตามสิทธิ์เจ้าของข้อมูลได้ (PDPA/GDPR)
- ทุกการเข้าถึงที่ต้องอนุมัติมีบันทึกบนการ์ด
