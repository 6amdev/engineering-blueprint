# ใช้งานจริง (operations)

> หลังปล่อยงาน: วัด เฝ้า แก้ เรียนรู้
> สถานะ: v0.3.0 (2026-11-21)

## Monitoring · logging · alerting (baseline)
อ้างอิง: Google SRE (สัญญาณ 4 ตัว: latency · traffic · errors · saturation)
- **Logging:** structured (JSON) · level ชัด · มี request/correlation id · ไม่ใส่ secret/PII · รวมศูนย์ · retention ตามนโยบาย (กรอกต่อโปรเจกต์: จำนวนวัน)
- **Metrics:** สัญญาณ 4 ตัวต่อ service + ตัววัดการใช้งานหลัก (เช่น การจองสำเร็จ/ล้มเหลว)
- **Health check:** liveness + readiness แยกกัน
- **Alert:** แจ้งเมื่อกระทบผู้ใช้ (symptom) มากกว่าสาเหตุภายใน · ทุก alert มีคนรับ + runbook · alert ที่ไม่มีใครลงมือ = ลบ/ปรับ
- เครื่องมือเฝ้าระบบใช้สิทธิ์อ่านอย่างเดียว
- **Dashboard:** หน้าเดียวเห็นสถานะรวม

## SLI / SLO / error budget
- SLI = ตัววัดจากมุมผู้ใช้ (สัดส่วนคำขอสำเร็จ · latency เปอร์เซ็นไทล์ที่ 95/99 · ความสดของข้อมูล)
- SLO = เป้า SLI ในช่วงเวลา เช่น "สำเร็จ ≥ 99.5% ใน 28 วัน" (กรอกต่อโปรเจกต์: ตัวเลขตามความสำคัญของระบบ)
- Error budget = 100% − SLO · ใช้ตัดสินใจ: งบเหลือ → ปล่อย feature ได้ · งบหมด/burn เร็ว → หยุด feature ทำ reliability/ถอย
- Alert ตาม burn rate (เร็ว = เตือนทันที · ช้า = ticket)
- ทบทวน SLO ทุกไตรมาส/retro

## On-call และระดับ incident
| ระดับ | ความหมาย | ตอบรับ | แจ้งสถานะ |
|---|---|---|---|
| SEV1 | ระบบล่ม/ข้อมูลเสียหายหรือรั่ว/ข้อมูลสำคัญทางธุรกิจผิด กระทบผู้ใช้ส่วนใหญ่ | ≤ 15 นาที (ตลอดเวลา) | ทุก 30 นาที |
| SEV2 | ฟังก์ชันหลักเสีย/ช้ามาก กระทบผู้ใช้บางส่วน ไม่มีทางเลี่ยง | ≤ 30 นาที (เวลาทำการ + on-call) | ทุก 1 ชม. |
| SEV3 | ฟังก์ชันรองเสีย มีทางเลี่ยง | ≤ 1 วันทำการ | เมื่อมีความคืบหน้า |
| SEV4 | ผลกระทบน้อย/รูปลักษณ์ | ตาม backlog | ในการ์ด |

ตัวเลขเป็นค่าเริ่มต้น ปรับต่อโปรเจกต์ได้ (กรอกต่อโปรเจกต์: ตารางเวร on-call · ช่องทางติดต่อ — ไม่ใส่ข้อมูลส่วนตัวใน repo)
- On-call: ผู้ถือเวร (Ops) + สำรอง · ส่งต่อเวรพร้อมสรุปสถานะ
- ข้อมูลส่วนบุคคลรั่ว = SEV1 เสมอ + แจ้ง Owner ทันที + ขั้นตอนแจ้งเจ้าของข้อมูล/หน่วยงานตามกฎหมาย (PDPA/GDPR มีกำหนดเวลา)

## Incident flow
1. ตรวจพบ (alert/ผู้ใช้แจ้ง) → เปิดการ์ด + กำหนด SEV
2. ตั้งผู้นำ incident (Ops) · ผู้ช่วยสืบ (`root-cause-analyst`) · ผู้สื่อสาร (`status-reporter` / Owner)
3. บรรเทาก่อนหาสาเหตุ: ถอย deploy / ปิด flag / scale / ปิดฟังก์ชัน · เก็บ log ก่อน restart ถ้าทำได้
4. ต้องแก้โค้ด → lane `hotfix` (skill `hotfix`: ย่อได้ แต่เทส RED · GATE-VERIFY · GATE-SEC (เมื่อแตะเส้นทางเสี่ยงสูง R3) · อนุมัติ · แผนถอย ข้ามไม่ได้)
5. ยืนยันกลับปกติด้วยตัวชี้วัด ไม่ใช่ความรู้สึก
6. Postmortem ภายใน 5 วันทำการสำหรับ SEV1–2 (skill `postmortem`, `templates/postmortem.md`)

## Runbook
- เก็บใน `docs/runbooks/` ใช้ `templates/ops-runbook.md` · หนึ่งเรื่อง/alert หนึ่งไฟล์
- มี: อาการ · ผลกระทบ · วิธีตรวจ (คำสั่งอ่านอย่างเดียวก่อน) · วิธีบรรเทา · วิธีถอย · ใครเรียกต่อ
- ซ้อม runbook (game day) อย่างน้อยปีละครั้ง

## Postmortem แบบ blameless
- เน้นระบบและกระบวนการ ไม่หาคนผิด · ลำดับเวลา · สาเหตุราก (5 whys) · อะไรทำงานดี · action items มีเจ้าของ + กำหนดเสร็จ
- action items เข้า backlog เป็นการ์ด · บทเรียนทั่วไปเข้า ADR หรือข้อเสนอแก้ blueprint (เขียนแบบ generic เท่านั้น)

## Backup และ restore drill
- Backup อัตโนมัติ: ความถี่ตาม RPO (กรอกต่อโปรเจกต์: RPO/RTO) · เก็บแยกที่/แยกสิทธิ์จากระบบหลัก · เข้ารหัส
- กฎ 3-2-1 เป็นแนวทาง (3 ชุด · 2 สื่อ · 1 นอกที่)
- Restore drill: กู้จริงบนสภาพแวดล้อมแยก ทุกไตรมาส · วัดเวลาเทียบ RTO · บันทึกผลบนการ์ด · backup ที่ไม่เคยกู้ = ยังไม่ใช่ backup
- ก่อนงาน R3 ที่แตะข้อมูล: backup ใหม่ + ตรวจว่ากู้ได้

## ตรวจสิทธิ์ · หมุน secret
- Access review ทุกไตรมาส (แนวคิด ISO 27001 Annex A: least privilege): ใครเข้า prod/DB/secret ได้ · ถอนสิทธิ์คนที่ย้ายงาน/ออก · บันทึกผล
- ห้ามบัญชีแชร์ · ทุกคนมีบัญชีของตัวเอง · บัญชีบริการแยกต่อระบบ สิทธิ์น้อยที่สุด
- Secret rotation ตามรอบ (กรอกต่อโปรเจกต์: เช่น 90 วัน) และทันทีเมื่อสงสัยรั่ว/คนออก · หลังหมุนทดสอบว่าระบบยังทำงาน · secret รั่วใน git = incident (หมุนทันที ไม่ใช่แค่ลบ commit)

## ปรับปรุง dependency (lane chore)
- รอบประจำ: รายเดือน (กรอกต่อโปรเจกต์) + ทันทีเมื่อมีช่องโหว่ระดับ high/critical (CVSS)
- ทำเป็นการ์ด `chore` · เปิด GATE-DEPS (SCA ช่องโหว่ + licence) · อัปทีละกลุ่มเล็ก · รันเทสทั้งชุดก่อน/หลัง ไม่มีเทสที่เคยผ่านแล้วกลับมาไม่ผ่าน
- patch/minor ตาม SemVer เสี่ยงน้อยกว่า major (major = อ่าน changelog + L2 บน UAT)
- เก็บ SBOM ของแต่ละ release (กรอกต่อโปรเจกต์: เครื่องมือ)
- runtime / OS / base image ต้องอยู่ในช่วง support (LTS)

## Capacity และ cost
- ดู saturation (CPU · memory · disk · connection · queue) และแนวโน้มการเติบโตรายไตรมาส · เตือนที่ ~70–80% ก่อนเต็ม
- ทดสอบโหลด (GATE-PERF) ก่อนเหตุการณ์ที่คาดว่าทราฟฟิกพุ่ง
- Cost: ทบทวนรายเดือน · ติดป้ายทรัพยากรตามระบบ · ปิดของที่ไม่ใช้ (UAT นอกเวลา, volume/snapshot ค้าง) · ตั้ง budget alert
- บันทึกข้อสังเกตลง retro
