# ด่าน (gates)

> สถานะ: v0.3.0 (2026-11-21) · รหัสตามหมวด ไม่ชนกัน
> ทุกด่าน: เป้า · ใครตรวจ (agent + คนอนุมัติ) · เปิดเมื่อไร · เกณฑ์ผ่าน (วัดได้) · หลักฐานที่แนบ · ไม่ผ่านแล้วทำอะไร
> ศัพท์ (R1–R3 · RED · oracle · sha) อยู่ `docs/workflow.md`

## หลัก: ด่านไม่ลด · ถูกปฏิเสธ = หยุดถาม
- ด่านเสมอเปิดทุกงาน · ด่านเงื่อนไขเปิดตอน intake (checklist ท้ายหน้า) · เปิดแล้วปิดกลางทางไม่ได้
- ความเร็วมาจากการเรียงลำดับและทำขนาน ไม่ใช่การข้ามด่าน
- ด่านส่วนใหญ่คน/agent ตรวจตาม checklist · ส่วนที่อัตโนมัติคือ git hook · secret scan · `draft-check` · CI ของโปรเจกต์
- hook / CI / ด่านปฏิเสธ = หยุด อ่านเหตุผล แก้ต้นเหตุ หรือถามคน · ห้ามอ้อม (`--no-verify`, ปิด hook, แก้เทสให้ผ่าน, ส่งต่อ session อื่น)
- หลักฐานทุกชิ้นอ้างได้: `file:line@sha` · คำสั่ง + บรรทัดผล · ลิงก์ผล CI · log query + ช่วงเวลา · ไม่ได้ตรวจ = เขียน "ยังไม่ได้ตรวจ"
- ผลด่านโพสต์ในการ์ด (`node scripts/board.mjs post <card> <file>`) · sha ที่ตรวจต้องตรงกับ sha ที่จะขึ้น · sha เปลี่ยน = เทสอัตโนมัติรันเต็มเสมอ · ด่านที่ agent/คนตรวจ: ตรวจ diff จาก sha ที่ด่านนั้นผ่านล่าสุด แล้วบันทึกทั้งสอง sha · ตรวจเต็มใหม่เมื่อ diff แตะเรื่องของด่านนั้น หรือเป็น R3
- กรอกต่อโปรเจกต์: คำสั่งตรวจของโปรเจกต์ (เทสทั้งชุด · lint · SCA · load test)

## คำตัดสิน: ผ่าน / ผ่านแบบมีเงื่อนไข / ไม่ผ่าน
- **ผ่าน** — เกณฑ์ครบทุกข้อ + หลักฐานครบ
- **ผ่านแบบมีเงื่อนไข** — ข้อที่ขาดไม่กระทบความถูกต้อง/ความปลอดภัย (เช่น เอกสารขาดถ้อยคำ) · ต้องมีเจ้าของ + กำหนดเสร็จ ก่อนขั้นถัดไป · **ใช้ไม่ได้** กับ GATE-SEC ข้อ High/Critical · GATE-VERIFY · GATE-PRIVACY · DB-WRITE
- **ไม่ผ่าน** — กลับไปขั้นที่ต้นเหตุอยู่ (เทสผิด spec = 2 · แบบผิด = 3 · โค้ด = 4) · แก้แล้วรันด่านนั้นใหม่ทั้งด่าน

## ด่านก่อนโค้ด

### GATE-SPEC (scope ก่อนออกแบบ)
- **เป้า:** spec ครบ ตรวจได้ ไม่เกินที่ owner ขอ
- **ใครตรวจ:** lead-reviewer (scope) · challenger (R2/R3 บังคับ) → **อนุมัติ:** Owner-reviewer ack
- **เปิด:** ทุกงานที่ทำขั้น 2
- **ผ่านเมื่อ:** ทุก acceptance criteria มีเทสอย่างน้อย 1 ในรายการเทส · ทุกข้อใน spec ชี้กลับ story ได้ · มี "ไม่ทำ" ชัด · ไม่มีข้อค้าน High จาก challenger เปิดค้าง
- **หลักฐาน:** link spec `docs/specs/<id>.md@sha` · ตาราง AC → test id · ผล challenger (ถ้าใช้)
- **ไม่ผ่าน:** กลับขั้น 1–2 · คำถามธุรกิจ → ถาม Owner (ก/ข + แนะนำ)

### GATE-DESIGN (แบบก่อนโค้ด)
- **เป้า:** ตัดสินใจโครงสร้างก่อนเขียน · มีเหตุผลรองรับ
- **ใครตรวจ:** solution-architect เขียน · lead-reviewer รีวิว (ใช้ approval-rehearsal ซ้อมคำถามก่อนส่งได้) → **อนุมัติ:** Owner-reviewer พูดคำว่า **"go"**
- **เปิด:** ทุกงานที่ทำขั้น 3
- **ผ่านเมื่อ:** design brief 5–8 บรรทัด (ไฟล์ที่แตะ · ข้อมูลไหลยังไง · ทางถอย) · ADR ของการตัดสินใจที่มีผลระยะยาว · ระบุ interface ที่เปลี่ยน · ไม่มีข้อรีวิว High ค้าง
- **หลักฐาน:** `docs/decisions/NNNN-*.md@sha` · comment "go" พร้อมวันที่ + บทบาท
- **ไม่ผ่าน:** แก้แบบ แล้วขอ "go" ใหม่ · ห้ามเริ่มโค้ดระหว่างรอ

## ด่านเสมอ (ทุกงาน)

### GATE-VERIFY (test-engineer)
- **เป้า:** เทสจับบั๊กได้จริง และไม่มีของเดิมพัง
- **ใครตรวจ:** test-engineer → **อนุมัติ:** Dev อ่านผล · R3 Owner-reviewer อ่านด้วย
- **ผ่านเมื่อ:** มีหลักฐานเทสที่ไม่ผ่านก่อนแก้ (เทสใหม่ไม่ผ่านบน base, ผ่านบน tip) · ทุกเทสในรายการเทสมีจริงและผ่าน · รันเทสทั้งชุดแล้วไม่มีเทสที่เคยผ่านแล้วกลับมาไม่ผ่าน · ไม่มีเทสถูกแก้ให้ตรงโค้ด (diff ของเทสเดิมอธิบายได้ด้วย spec)
- **หลักฐาน:** คำสั่ง + บรรทัดผลก่อนแก้/หลังแก้ · ผลเทสทั้งชุดของ base และ tip (ลิงก์ CI หรือผลรันในเครื่อง) + sha ทั้งสอง · รายการ test id
- **ไม่ผ่าน:** กลับขั้น 4 · เทสที่ผลไม่คงที่ (flaky) ห้ามนับว่าผ่าน → แยกการ์ด `bug` แต่ด่านนี้ยังไม่ผ่านจนรันซ้ำนิ่ง

### GATE-SEC (security-engineer)
- **เป้า:** ไม่เปิดช่องโหว่ใหม่ ตาม OWASP Top 10 / ASVS ตามระดับ R
- **ใครตรวจ:** security-engineer (skill `security-review`) → **อนุมัติ:** Dev (R1–R2) · คนที่ไม่ใช่ผู้เขียน (R3 · ทีมคนเดียวดู `docs/roles/README.md`)
- **ระดับ:** R1 = checklist พื้นฐาน (secret · input · authz) · R2 = ASVS L1 · R3 = ASVS L2 ส่วนที่เกี่ยว · lane `hotfix` = เต็มเมื่อแตะเส้นทางเสี่ยงสูง (R3)
- **ผ่านเมื่อ:** `npm run secret-scan` ผ่าน · ผ่าน checklist ตามระดับ · ไม่มีข้อ High/Critical (CVSS ≥ 7.0) เปิดค้าง · input ทุกจุดใหม่ validate ฝั่ง server · authz ตรวจทุก endpoint ใหม่ · ไม่ log ค่าลับ/PII
- **หลักฐาน:** ตาราง finding (ข้อ · ระดับ · `file:line@sha` · สถานะ) · บรรทัดผล secret-scan
- **ไม่ผ่าน:** High/Critical = บล็อก กลับขั้น 4 · Medium = แก้ก่อน deploy หรือ Owner-reviewer รับความเสี่ยงเป็นลายลักษณ์ (ความเห็นลงวันที่ + ADR) · Low = เข้า backlog

### GATE-REGRESSION (regression-tester)
- **เป้า:** พฤติกรรมเดิมที่ไม่อยู่ใน scope ยังเหมือนเดิม · contract กับระบบรอบข้างไม่แตก
- **ใครตรวจ:** regression-tester → **อนุมัติ:** Dev
- **ผ่านเมื่อ:** diff แตะแค่ไฟล์ที่ design brief บอก (ส่วนเกินต้องอธิบายได้) · API/schema/event ที่ระบบอื่นใช้ไม่เปลี่ยนแบบไม่เข้ากัน (หรือมี version ใหม่ + ADR) · migration ย้อนได้หรือมีแผนถอย · ข้อความผู้ใช้เดิมไม่เปลี่ยนโดยไม่ได้ ack
- **หลักฐาน:** รายการไฟล์ใน diff เทียบ brief · ผล contract test · `file:line@sha` ของจุดที่เปลี่ยน interface
- **ไม่ผ่าน:** กลับขั้น 3 (ถ้าแบบต้องเปลี่ยน) หรือ 4

### code review (lead-reviewer / คน)
- **เป้า:** อ่านรู้เรื่อง ถูกต้อง ดูแลต่อได้
- **ใครตรวจ:** lead-reviewer (skill `code-review`, `templates/code-review.md`) + คนตามระดับ R (`docs/workflow.md`)
- **ผ่านเมื่อ:** ไม่มีข้อ blocking ค้าง · ทุก comment ได้คำตอบ · R3 มีคนอนุมัติที่ไม่ใช่ผู้เขียน (ทีมคนเดียวดู `docs/roles/README.md`) · commit เป็น Conventional Commits
- **หลักฐาน:** ผลรีวิวในการ์ด/PR · บทบาทผู้อนุมัติ + วันที่ + sha
- **ไม่ผ่าน:** แก้แล้วรีวิวรอบใหม่บน sha ใหม่

## ด่านเงื่อนไข (เปิดตอน intake)

### GATE-UI (qa-engineer · หน้าจริง)
- **เปิดเมื่อ:** UI เปลี่ยน
- **เป้า:** หน้าจริงใช้ได้บนจอเล็กและทุกธีม
- **ใครตรวจ:** qa-engineer → **อนุมัติ:** Frontend
- **ผ่านเมื่อ:** ตรวจในเบราว์เซอร์จริงที่ 375px และเดสก์ท็อป · ธีมสว่างและมืด · ไม่มี scroll แนวนอน · ไม่มี console error · ทุก state (ว่าง · โหลด · error · ไม่มีสิทธิ์) แสดงถูก · ข้อความตรงที่ owner ack
- **หลักฐาน:** ภาพหน้าจอต่อ state × ขนาด × ธีม · URL + sha ที่ตรวจ
- **ไม่ผ่าน:** กลับขั้น 4 · ข้อความ/ดีไซน์ไม่ชัด → ถาม Owner

### GATE-PERF (qa-engineer)
- **เปิดเมื่อ:** งานแตะ latency ที่ผู้ใช้รู้สึก · ข้อมูลปริมาณมาก · query หนัก · งาน batch · คาดผู้ใช้พร้อมกันเพิ่ม
- **ใครตรวจ:** qa-engineer → **อนุมัติ:** Dev + Ops
- **ผ่านเมื่อ:** ตัวเลขตาม budget ที่เขียนใน spec · กรอกต่อโปรเจกต์: budget จริง (ค่าแนะนำเริ่มต้น: API p95 ≤ 300 ms · หน้าเว็บ LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 บนมือถือ) · load test ที่ 2 เท่าของ peak ที่คาด error rate < 1% · query ใหม่ใช้ index (ไม่อ่านทั้งชุดข้อมูลใหญ่)
- **หลักฐาน:** คำสั่ง load test + สภาพแวดล้อม + ผล p50/p95/p99 · แผนการรันของ query
- **ไม่ผ่าน:** กลับขั้น 3–4 · budget ต้องเปลี่ยน = Owner-reviewer ตัดสิน + ADR

### GATE-A11Y (qa-engineer)
- **เปิดเมื่อ:** มี UI ที่ผู้ใช้เห็น (ใหม่หรือเปลี่ยน)
- **ใครตรวจ:** qa-engineer → **อนุมัติ:** Frontend
- **ผ่านเมื่อ:** WCAG 2.2 AA: contrast ข้อความ ≥ 4.5:1 (ตัวใหญ่ ≥ 3:1) · ใช้ได้ด้วยคีย์บอร์ดล้วน · focus มองเห็น · ทุก input มี label · รูปมี alt · เป้าแตะ ≥ 24×24 px (แนะนำ 44×44) · ไม่มีข้อ critical/serious จากเครื่องมือตรวจอัตโนมัติ
- **หลักฐาน:** ผลเครื่องมือตรวจ (ชื่อ + version + จำนวนข้อ) · checklist ตรวจมือ
- **ไม่ผ่าน:** กลับขั้น 4

### GATE-PRIVACY (security-engineer)
- **เปิดเมื่อ:** เก็บ/อ่าน/ส่ง/ลบข้อมูลส่วนบุคคล
- **ใครตรวจ:** security-engineer → **อนุมัติ:** Owner (และผู้ดูแลข้อมูลส่วนบุคคลขององค์กร ถ้ามี)
- **ผ่านเมื่อ:** data inventory (field · มาจากไหน · เก็บที่ไหน) · วัตถุประสงค์ + ฐานทางกฎหมายต่อ field · เก็บเท่าที่จำเป็น · ระยะเวลาเก็บ + วิธีลบ · ใครเข้าถึงได้ (least privilege) · เข้ารหัสระหว่างส่งและตอนเก็บสำหรับข้อมูลอ่อนไหว · ไม่อยู่ใน log/การ์ด/เทส fixture · รองรับคำขอเจ้าของข้อมูล (ดู · แก้ · ลบ) ตาม PDPA/GDPR
- **หลักฐาน:** ตาราง data inventory ใน spec · `file:line@sha` ของจุดเก็บ/ลบ · ผลค้น log ว่าไม่มี PII
- **ไม่ผ่าน:** บล็อก deploy · ฐานทางกฎหมายไม่ชัด → ถาม Owner

### GATE-DEPS (security-engineer)
- **เปิดเมื่อ:** เพิ่มหรืออัป dependency (บังคับใน lane `chore` ที่อัป dependency)
- **ใครตรวจ:** security-engineer → **อนุมัติ:** Dev
- **ผ่านเมื่อ:** SCA (เช่น `npm audit` หรือเทียบเท่า) ไม่มีช่องโหว่ High/Critical ที่ใช้ถึง · version ปักตายตัว + lockfile อัป · licence เข้ากับโปรเจกต์ (กรอกต่อโปรเจกต์: รายการ licence ที่รับได้) · package ยังมีคนดูแล (release ล่าสุด ≤ 12 เดือน) · ไม่ใช่ชื่อเลียนแบบ (typosquat) · SBOM อัปถ้าโปรเจกต์ทำ SBOM
- **หลักฐาน:** คำสั่ง audit + บรรทัดสรุป · ตาราง package · version · licence · เหตุผลที่เพิ่ม
- **ไม่ผ่าน:** หาเวอร์ชันอื่น/ทางอื่น (stdlib ก่อน) · รับความเสี่ยงได้เฉพาะช่องโหว่ และต้องมี ADR · licence ขัดกันรับไม่ได้

### GATE-OBS (runbook-rehearsal / Ops)
- **เปิดเมื่อ:** ก่อนขึ้น prod ครั้งแรกของ service/ฟีเจอร์ใหม่ · งานที่เปลี่ยนเส้นทางสำคัญ
- **ใครตรวจ:** runbook-rehearsal → **อนุมัติ:** Ops
- **ผ่านเมื่อ:** log มีโครง (มี request id · ไม่มีค่าลับ/PII) · metric ตาม SLI ที่ตกลง · SLO เขียนไว้ใน `docs/operations.md` · alert ผูก error budget burn (ไม่ใช่ทุก error) และส่งถึงคนจริง · dashboard เห็นสุขภาพใน 1 หน้า · runbook ต่อ alert ใน `docs/runbooks/` · ทางถอยเขียนแล้ว
- **หลักฐาน:** link dashboard/alert config · path runbook@sha · ผลยิง alert ทดสอบบน UAT
- **ไม่ผ่าน:** ห้ามขึ้น prod

## ด่านปฏิบัติการ

### DB-READ (อ่านข้อมูลจริง)
- **เป้า:** อ่าน DB prod โดยไม่กระทบระบบและไม่ทำข้อมูลหลุด
- **ใครตรวจ:** ผู้เตรียม (prod-reader หรือ Dev) ไล่ checklist ใน `docs/db-scripts.md` → **อนุมัติ:** Ops · prod-reader รันหลังได้อนุมัติเท่านั้น
- **ผ่านเมื่อ:** checklist ครบ · เทสผ่าน · ลองบน UAT หรือข้อมูลทดสอบแล้ว · มีการอนุมัติอ่านข้อมูลจริงที่ผูกกับ hash ของสคริปต์ และ hash ตรงกับไฟล์ที่จะรัน · ผลไม่พิมพ์ id/PII
- **หลักฐาน:** path + sha256 + commit · ผลเทส · บรรทัดอนุมัติพร้อมวันที่
- **ไม่ผ่าน:** แก้ไฟล์ = hash ใหม่ = ขออนุมัติใหม่

### DB-WRITE (dry-run · allowlist · backup)
- **ผ่านเมื่อ:** dry-run เป็นค่าเริ่มต้นและรันแล้วผลตรงที่คาด · ตรวจชื่อ DB · allowlist ของชุดข้อมูลที่แก้ได้ · backup + วิธีถอยพร้อมก่อน apply · Ops อนุมัติก่อน apply · R3 เสมอ
- **ใครตรวจ:** security-engineer + Dev ที่ไม่ใช่ผู้เขียน (ถ้ามี) → **อนุมัติ:** Ops + Owner-reviewer
- **หลักฐาน:** ผล dry-run (จำนวนระเบียน) · เลขอ้างอิง backup · บรรทัดอนุมัติ
- **ไม่ผ่าน:** ห้าม apply · ไม่มีผ่านแบบมีเงื่อนไข

### DEP (ใบขอ deploy)
- **ผ่านเมื่อ:** `templates/deploy-request.md` กรอกครบทุกข้อ · UAT ผ่านบน sha เดียวกัน · ด่านที่ผูก sha ผ่านบน sha นี้ (แนบผล CI) · rollback sha + ขั้นถอยเขียนแล้ว · GATE-OBS ผ่าน (ถ้าเปิด)
- **ใครตรวจ:** uat-release เตรียม (skill `deploy-request`) · ผู้อนุมัติไล่ checklist ในใบเอง → **อนุมัติ:** Ops + Owner-reviewer (R2/R3)
- **หลักฐาน:** link ใบขอ · ลิงก์ผลด่าน/CI · บรรทัดอนุมัติ
- **ไม่ผ่าน:** แก้ใบ · sha เปลี่ยน = ทำด่านที่ผูก sha ใหม่

### POST (draft-check)
- **ผ่านเมื่อ:** `node scripts/draft-check.mjs <draft.md>` พิมพ์ `OK` · `board.mjs post` เรียกให้เองทุกครั้ง
- **สคริปต์ตรวจ:** ค่าลับ · IP สาธารณะ · คำต้องห้ามใน config · commit hash เต็ม 40 ตัวที่ไม่มีใน repo · ลายเซ็นท้ายโพสต์ (ถ้าตั้งไว้)
- **คนที่โพสต์ตรวจเอง:** ข้อมูลส่วนบุคคล · รูปแบบโพสต์ · ความถูกต้องของเนื้อหา · ไม่ตีความความเงียบเป็นการอนุมัติ
- **ไม่ผ่าน:** แก้ร่างแล้วรันใหม่ · ห้ามโพสต์ด้วยทางอื่นเพื่อเลี่ยง

## เปิดด่านไหนบ้าง (checklist ตอน intake)
ตอบทุกข้อในการ์ด · "ใช่" ข้อไหน = เปิดด่านนั้น · ไม่แน่ใจ = เปิด
- [ ] UI ที่ผู้ใช้เห็นเปลี่ยนไหม → GATE-UI + GATE-A11Y
- [ ] มีเป้าความเร็ว · ข้อมูลเยอะ · query หนัก · batch · ผู้ใช้พร้อมกันเพิ่มไหม → GATE-PERF
- [ ] แตะข้อมูลส่วนบุคคล (เก็บ · อ่าน · ส่ง · ลบ · export) ไหม → GATE-PRIVACY + R3
- [ ] เพิ่ม/อัป dependency ไหม → GATE-DEPS
- [ ] ขึ้น prod ครั้งแรก · service ใหม่ · เปลี่ยนเส้นทางสำคัญไหม → GATE-OBS
- [ ] แตะ auth · สิทธิ์ · ข้อมูลสำคัญทางธุรกิจ · ข้อมูลย้อนไม่ได้ไหม → R3 (GATE-SEC ระดับ ASVS L2 + คนอนุมัติที่ไม่ใช่ผู้เขียน)
- [ ] ต้องอ่าน/เขียน DB prod ไหม → DB-READ / DB-WRITE
- [ ] lane + ระดับ R ที่เลือก: <lane> · <R>
