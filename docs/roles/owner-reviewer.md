# Owner + Owner-reviewer

> Owner = ตัดสินเรื่องธุรกิจ · Owner-reviewer = ตรวจว่าทำถูกและปลอดภัย · ทีมเล็กอาจเป็นคนเดียวกัน

## หน้าที่
- **Owner:** เป้าหมายและวัดผล · ลำดับ backlog (skill `planning`) · กฎธุรกิจ · ข้อความที่ผู้ใช้เห็น · ack brief / PRD / change request
- **Owner-reviewer:** ack scope (ขั้น 2) · ให้ "go" แบบ (ขั้น 3) · อ่านผลด่าน (ขั้น 5) · ตัดสิน UAT (ขั้น 6) · ตรวจใบ deploy (ขั้น 7) · ปิด DoD (ขั้น 9)

## คำตัดสินที่ถือ
- ทำ / ไม่ทำ / เลื่อน · ขอบเขต "ไม่ทำ" · ระดับความเสี่ยง R ขั้นสุดท้าย
- เปิดด่านเงื่อนไขไหน (UI · PERF · A11Y · PRIVACY · DEPS · OBS) — ตั้งตอน intake ปิดทีหลังไม่ได้
- ข้อยกเว้น (ผ่านแบบมีเงื่อนไข) — มีขอบเขต วันหมดอายุ และการ์ดติดตามเสมอ

## คำอนุมัติ + บันทึกบนการ์ด
ทุกคำเป็นความเห็นบนการ์ด มีวันที่ · บทบาท · sha หรือลิงก์ของสิ่งที่อนุมัติ
| คำ | ขั้น | ตัวอย่างบรรทัด |
|---|---|---|
| ack brief / PRD | 0–1 | `ACK brief · Owner · 2026-11-21 · docs/requirements/0001-room-booking.md@<sha>` |
| ack scope | 2 | `ACK scope SP-0001 · Owner-reviewer · <วันที่> · spec@<sha>` |
| "go" | 3 | `go · Owner-reviewer · <วันที่> · ADR-0003@<sha>` |
| ผลด่าน | 5 | `GATES ผ่าน · Owner-reviewer · <วันที่> · commit <sha>` |
| UAT | 6 | `UAT ผ่าน · Owner-reviewer · <วันที่> · sha <sha> · ช่วง <เวลา>` |
| รับความเสี่ยง R3 (ทีมคนเดียว) | ก่อน "go" / deploy | `รับความเสี่ยง R3 ไม่มีคนที่สอง · Owner · <วันที่> · sha <sha> · เหตุผล <…>` |
| DoD | 9 | `DONE · Owner-reviewer · <วันที่> · release <version>` |

การอนุมัติอ่านข้อมูลจริงอยู่กับ Ops (`docs/db-scripts.md`)
เปลี่ยนไฟล์หลังอนุมัติ = sha ใหม่ = ขอใหม่ · คำว่า "ok" ลอย ๆ ไม่นับเป็นคำอนุมัติ

## กติกาตัดสิน
- ด่านไม่ลด · เร็วขึ้นได้ด้วยลำดับ ไม่ใช่ด้วยการข้าม
- ไม่ตอบแทน Owner จากความจำ · ไม่มีคำตอบบนการ์ด = ยังไม่ตัดสิน
- ข้อยกเว้นต้องมี: ขอบเขต (ไฟล์ / ฟังก์ชัน) · เหตุผล · วันหมดอายุ · การ์ดติดตาม
- งาน R3 ที่ตัวเองเขียน → หาคนที่สอง · ไม่มีจริง ๆ ใช้การรับความเสี่ยงที่บันทึกไว้ (ดู `README.md`)
- ความเงียบไม่ใช่การอนุมัติ

## checklist ดูคำขออ่านข้อมูลจริง (ช่วย Ops)
- [ ] จำเป็นจริง · ตอบคำถามที่เขียนไว้
- [ ] อ่านอย่างเดียว · ชื่อ DB และชุดข้อมูลตรงเป้าหมาย · จำกัดผลลัพธ์และช่วงเวลา
- [ ] ไม่ดึงข้อมูลส่วนบุคคลเกินจำเป็น (เลือก field · ปิดบัง)
- [ ] hash ในคำขอตรงกับไฟล์ที่จะรัน · มีผลเทส
- [ ] ผลจะไปเก็บที่ไหน ใครเห็น ลบเมื่อไร

## checklist ตรวจแผน / ใบ deploy
- [ ] sha ที่จะขึ้น = sha ที่ผ่าน UAT
- [ ] ใบกรอกครบ · ผล CI และด่านอยู่บน sha เดียวกัน
- [ ] ลำดับเป้าหมาย · จุดตรวจระหว่างขั้น · เกณฑ์หยุด
- [ ] แผนถอยลองแล้ว (อย่างน้อยบน UAT) · เวลาที่ใช้ถอย
- [ ] migration ย้อนได้ หรือมี backup + วิธีกู้
- [ ] GATE-OBS (ถ้าเปิด): log · metric · alert · dashboard · runbook มีจริง
- [ ] ช่วงเวลา deploy + ใครเฝ้าหลังขึ้น นานเท่าไร

## ผ่าน / ผ่านแบบมีเงื่อนไข / ไม่ผ่าน
- **ผ่าน:** ครบทุกข้อ · ไม่มีข้อค้าง
- **ผ่านแบบมีเงื่อนไข:** เขียนเงื่อนไข + เจ้าของ + วันครบ + การ์ดติดตาม · ด่านที่ใช้ไม่ได้อยู่ใน `docs/gates.md`
- **ไม่ผ่าน:** ระบุข้อ + ที่มา (`file:line@sha` / บรรทัดผลคำสั่ง) + ต้องทำอะไรถึงจะผ่าน

## สิ่งที่ถามเสมอ
- วัดว่าสำเร็จด้วยอะไร · อะไรที่ **ไม่ทำ**
- ถ้าพังบน prod ถอยยังไง ใช้เวลาเท่าไร
- ใครได้รับผลกระทบ แจ้งเขาหรือยัง
- แตะข้อมูลส่วนบุคคล / ข้อมูลสำคัญทางธุรกิจ / สิทธิ์ ไหม → ด่านไหนครอบ
- ข้อไหน "ยังไม่ได้ตรวจ"

## จังหวะ
- ทุกวัน: อ่านการ์ดที่รอตัวเอง (ack · go · ผลด่าน · ใบ deploy) ตอบภายในเวลาตอบที่ทีมตกลง
- ทุกสัปดาห์: จัด backlog + WIP limit (skill `planning`) · ดูข้อยกเว้นที่ใกล้หมดอายุ
- หลัง release / ทุก N การ์ด: retro (skill `retro`) · บทเรียน → ADR

## ไม่ทำ
- ไม่ปล่อยให้คำอนุมัติค้างในแชตหรือปากเปล่า ต้องถูกบันทึกบนการ์ด (กติกา `docs/posting.md`)
- ไม่อนุมัติสิ่งที่ไม่มี sha / ลิงก์
- ไม่สั่งข้ามด่าน ไม่สั่งปิด hook
- ไม่แก้โค้ดที่ตัวเองกำลังตรวจ
