# Workflow — จากคำขอถึง production

> สถานะ: v0.3.0 (2026-11-21) · ปรับเพิ่มเมื่อใช้จริงแล้วเจอจุดต้องแก้ (บันทึกเป็น ADR)
> หลัก: ขั้นข้ามได้ตาม lane + ระดับ R ที่ตารางนี้บอกเท่านั้น · **ด่านไม่ข้าม** (`docs/gates.md`)

## ศัพท์ที่ใช้ทั้ง blueprint
| คำ | ความหมาย |
|---|---|
| R1 · R2 · R3 | ระดับความเสี่ยง ต่ำ · กลาง · สูง · **R3** = auth/สิทธิ์ · ข้อมูลสำคัญทางธุรกิจ (เช่น ข้อมูลการเงิน) · ข้อมูลที่แก้แล้วย้อนไม่ได้ · ข้อมูลส่วนบุคคล · ความปลอดภัย |
| L1 · L2 | ระดับเทส: L1 = unit/integration ใน dev/CI · L2 = ทดสอบผ่านระบบจริงบน UAT |
| RED | เทสที่เขียนก่อนแก้โค้ดและยังไม่ผ่าน · เก็บผลไว้เป็นหลักฐานว่าเทสจับปัญหาได้จริง · GREEN = ผ่านหลังแก้ |
| oracle | แหล่งที่บอกว่าผลที่ถูกคืออะไร · ใน blueprint นี้คือ spec ที่ยืนยันแล้ว |
| ADR | Architecture Decision Record: บันทึกการตัดสินใจที่มีผลระยะยาว พร้อมทางเลือกและเหตุผล |
| UAT | User Acceptance Testing: ทดสอบเพื่อยอมรับงาน บนสภาพแวดล้อมใกล้ prod |
| DoR · DoD | Definition of Ready · Definition of Done: เกณฑ์เริ่มงาน · เกณฑ์ปิดงาน |
| sha | รหัส commit ของ git ระบุเวอร์ชันโค้ดแบบเจาะจง · **sha256** = hash ของไฟล์ ใช้ยืนยันว่าไฟล์ไม่เปลี่ยนหลังตรวจ |

## ภาพรวม
```
planning ─▶ 0 intake ─▶ 1 requirements ─▶ 2 spec ─▶ 3 design ─▶ 4 build (RED→GREEN) ─▶ 5 gates
   ─▶ 6 UAT ─▶ 7 deploy ─▶ 8 release + คู่มือ ─▶ 9 close (DoD + HANDOFF) ─▶ retro (ทุกรอบ release / ทุก N การ์ด)
```

| ขั้น | ทำอะไร | skill / agent | ออกจากขั้นเมื่อ | งานเล็กข้ามได้? |
|---|---|---|---|---|
| 0 intake | ถามครบตาม `docs/intake-map.md` ถึง tech stack · ได้ brief · เลือก lane · ตั้งระดับ R · เปิดด่านเงื่อนไข | `intake` · `grill` · intake-analyst | brief ผ่าน **DoR** + owner ยืนยัน | ไม่ |
| 1 requirements | PRD + user stories + Given/When/Then | `requirements` · intake-analyst | owner ack | ได้ (brief พอ) ถ้า R1 |
| 2 spec | spec + oracle + รายการเทส · challenger ค้าน (R2/R3 บังคับ) | `spec` · solution-architect · challenger · lead-reviewer | Owner-reviewer ack scope (GATE-SPEC) | ได้ถ้า R1 |
| 3 design | ADR + design brief 5–8 บรรทัด · มีหน้าจอ: เลือกจากภาพร่าง | `design` · `ui-design` · solution-architect | review ผ่าน + คำว่า **"go"** (GATE-DESIGN) | ได้ถ้า R1 |
| 4 build | เทส RED → โค้ด → refactor | `tdd` · implementer | เทสใหม่ผ่าน · ไม่มีเทสที่เคยผ่านแล้วกลับมาไม่ผ่าน | ไม่ |
| 5 gates | ด่านเสมอ + ด่านเงื่อนไขที่เปิดไว้ตอน intake | `gate-check` · `code-review` · `security-review` · agent ตามด่าน (`docs/gates.md`) | ทุกด่านที่เปิด = ผ่าน | ไม่ |
| 6 UAT | ประกาศ sha + ช่วงเวลา → ขึ้น UAT → L2 + หน้าจริง (เมื่อ UI เปลี่ยน) | `uat` · uat-release · qa-engineer | เกณฑ์ผ่านทุกข้อบน UAT | ไม่ (hotfix ย่อช่วงเวลาได้) |
| 7 deploy | ใบขอ deploy + runbook → ops ขึ้นทีละเป้าหมาย | `deploy-request` · runbook-rehearsal · Ops | ด่าน DEP ผ่าน · เฝ้าหลังขึ้นครบ | — |
| 8 release | release notes + CHANGELOG + คู่มือผู้ใช้ | `release-notes` · `user-manual` · tech-writer | `npm run docs:build` ผ่าน | ได้ถ้าผู้ใช้ไม่เห็นความต่าง |
| 9 close | DoD + อัป HANDOFF + memory + commit | `handoff` · status-reporter | DoD ครบ | ไม่ |

## รอบนอก workflow
- **planning ก่อน intake** (skill `planning`): backlog `docs/backlog.md` → จัดลำดับ (RICE หรือ MoSCoW) → ขนาด T-shirt (S/M/L/XL) → roadmap → intake หยิบการ์ดบนสุดที่ไม่ติดอะไร · XL = แตกก่อนหยิบ
- **retro หลัง release หรือทุก N การ์ด** (skill `retro`, `templates/retro.md`): ดู DORA + เหตุการณ์ → action ≤ 3 ข้อมีเจ้าของ · บทเรียน → ADR หรือข้อเสนอแก้ blueprint (เขียนเป็นหลักทั่วไปเท่านั้น)
- กรอกต่อโปรเจกต์: ค่า N ของ retro (แนะนำ 5 การ์ด หรือทุก 2 สัปดาห์ แล้วแต่ถึงก่อน)

## ช่องทางงาน (lanes)
เลือก lane ตอน intake · เขียนในการ์ด · เปลี่ยน lane กลางทาง = กลับ intake

| ขั้น | `feature` | `change` | `bug` | `hotfix` | `chore` |
|---|---|---|---|---|---|
| 0 intake | ต้อง | ต้อง (ใบ change-request) | ต้อง (ใบ bug-report) | ต้อง (ย่อ 5 บรรทัด) | ต้อง (ย่อ) |
| 1 requirements | ต้อง | ย้อนถ้ากระทบ | ข้ามได้* | ย่อได้ | ข้าม |
| 2 spec | ต้อง | ย้อนถ้ากระทบ | ข้ามได้* | ย่อได้ | ข้าม |
| 3 design | ต้อง | ย้อนถ้ากระทบ | ข้ามได้* | ย่อได้ (brief 3 บรรทัด) | ข้ามได้ (refactor ใหญ่ = ต้อง) |
| 4 build — เทส RED | **ห้ามข้าม** | **ห้ามข้าม** | **ห้ามข้าม** | **ห้ามข้าม** | **ห้ามข้าม** (refactor: เทสเดิมต้องผ่านทั้งก่อนและหลัง) |
| 5 gates | **ห้ามข้าม** | **ห้ามข้าม** | **ห้ามข้าม** | **ห้ามข้าม** (VERIFY · SEC เมื่อแตะเส้นทางเสี่ยงสูง R3) | **ห้ามข้าม** (+ GATE-DEPS ถ้าแตะ dependency) |
| 6 UAT | ต้อง | ต้อง | ต้อง | ย่อช่วงเวลาได้ · ไม่ข้าม smoke | ต้อง (smoke) |
| 7 deploy + แผนถอย | ต้อง | ต้อง | ต้อง | **ห้ามข้าม** + Owner/Ops อนุมัติ | ต้อง |
| 8 release | ต้อง | ต้อง | ถ้าผู้ใช้เห็น | ต้อง (สั้น) | ข้ามได้ (CHANGELOG ยังลง) |
| 9 close | ต้อง | ต้อง | ต้อง | ต้อง + postmortem | ต้อง |

\* bug ข้าม 1–3 ได้ เมื่อการแก้ทำให้ระบบกลับมาตรง spec เดิม · ถ้าการแก้เปลี่ยนพฤติกรรม/spec = ทำ 1–3 (หรือเปลี่ยนเป็น `change`)
- **ข้ามได้** = ไม่ต้องสร้างเอกสารใหม่ แต่เขียนในการ์ด 1 บรรทัดว่าข้ามเพราะอะไร
- **ห้ามข้าม** = ไม่มีข้อยกเว้น ทั้งระดับ R และความด่วน

## ระดับ R เปลี่ยนขั้นบังคับยังไง
| | R1 ต่ำ | R2 กลาง | R3 สูง |
|---|---|---|---|
| 1–3 | ข้ามได้ (brief ย่อ + ADR สั้นถ้ามีการตัดสินใจที่มีผลระยะยาว) | 1 ย่อได้ (brief ย่อถ้ามี flow เดียว) · 2–3 ต้อง | ต้องครบ |
| GATE-SEC | checklist พื้นฐาน (secret · input · authz) | ASVS L1 | ASVS L2 |
| code review | AI reviewer 1 | AI + คน 1 | AI + คน 1 ที่ **ไม่ใช่คนเขียน** (ทีมคนเดียว: ดู `docs/roles/README.md`) |
| UAT | smoke + เกณฑ์ผ่าน | เกณฑ์ผ่านครบ | เกณฑ์ผ่านครบ + เคสผิดปกติ + ซ้อมถอย |
| deploy | ปกติ | ทีละเป้าหมาย + เฝ้า | ทีละเป้าหมาย + สวิตช์ปิด (feature flag) + ซ้อมแผนถอยแล้ว |
- R ปรับขึ้นได้ตลอด (เจอของเสี่ยงกลางทาง = ขึ้น R แล้วทำขั้นที่ขาดย้อนหลัง) · ปรับลงต้อง Owner-reviewer ยืนยันในการ์ด

## จุดอนุมัติตามระดับ R (ลดการขอ ไม่ลดด่าน)
ด่านทุกด่านยังทำครบ ต่างกันที่จำนวนครั้งที่ต้องรอคน · ตารางขั้นและ RACI ด้านบนคือแบบเต็ม (R3)

| | R1 ต่ำ | R2 กลาง | R3 สูง |
|---|---|---|---|
| ก่อนเขียนโค้ด | ไม่ขอต่อการ์ด ถ้า Owner อนุมัติล่วงหน้าทั้งโปรเจกต์ไว้ใน ADR (ไม่มี ADR = ใช้แบบ R2) | **"go" ครั้งเดียว** รวม ACK brief + scope + แบบ | ACK brief · ACK scope · "go" แยกกัน |
| หลังด่าน | **ตรวจรับครั้งเดียว** | **ตรวจรับครั้งเดียว** รวมผลด่าน + UAT | ผลด่าน · UAT แยกกัน + คนที่สอง |
| ขึ้น prod | Ops | Ops + Owner-reviewer | Ops + Owner-reviewer + คนที่สอง |
- **ตารางนี้เป็นหลัก:** skill · agent · แม่แบบ · RACI ที่บอกให้ขอ ACK ต่อขั้น ใช้กับ R3 · R1/R2 รวมตามตาราง (เอกสารและด่านยังทำครบ)
- intake ยังถามคำถามธุรกิจได้ทุกระดับ · ความเงียบไม่ใช่การอนุมัติทุกระดับ
- **มอบอำนาจต่อการ์ด:** Owner มอบล่วงหน้าได้เฉพาะ R1/R2 ที่ไม่ขึ้น prod บันทึกบนการ์ดว่ามอบเรื่องอะไร · ยังต้องถามเสมอ: push/เผยแพร่ · ลบข้อมูล · ระบบจริง · เปลี่ยนขอบเขต · hook หรือด่านปฏิเสธ · ผลที่ agent ตรวจแทนคนต้องเขียนว่า "ตรวจโดย agent"

## Definition of Ready (เริ่มขั้น 1 ได้เมื่อครบ · ที่เดียว แม่แบบอ้างมาที่นี่)
- [ ] ปัญหา/เป้าหมาย + วัดความสำเร็จด้วยอะไร
- [ ] ผู้ใช้ + บทบาท + อุปกรณ์
- [ ] ขอบเขต: ทำ / **ไม่ทำ**
- [ ] flow หลัก + เคสผิดปกติหลัก
- [ ] acceptance criteria ≥ 1 ต่อ flow (Given/When/Then)
- [ ] `docs/stack-decisions.md` ตอบครบทุกบรรทัด (งานใหม่ถามครบ · งานต่อยอดถามเฉพาะที่เปลี่ยน) · ไม่มี ❓
- [ ] ข้อมูล · PII · สิทธิ์ · ระบบรอบข้าง ระบุแล้ว · NFR ที่เกี่ยวมีตัวเลข (ตัวเลขที่ agent เติมเองอยู่ในหัวข้อ "ข้อสมมติ")
- [ ] ความเสี่ยง + ระดับ R เบื้องต้น · lane · ด่านเงื่อนไขที่เปิด (checklist ใน `docs/gates.md`)
- [ ] รู้ว่าใครตัดสินเรื่องไหน
- [ ] มีสิทธิ์ใช้ระบบ ข้อมูล และเนื้อหาที่งานแตะ · ไม่มีข้อกฎหมายที่ยังไม่ชัด
- [ ] ข้อที่ยังไม่รู้เขียนชัดว่า "ยังไม่ได้ตรวจ / รอ <ใคร>" และไม่บล็อกการเริ่ม

## Definition of Done (ปิดการ์ดได้เมื่อครบ)
- [ ] ทำครบทุกข้อใน scope · ไม่เกินขอบเขต
- [ ] เทส: มีหลักฐานเทสที่ไม่ผ่านก่อนแก้ · เทสใหม่ผ่าน · ไม่มีเทสที่เคยผ่านแล้วกลับมาไม่ผ่าน (แนบผล CI)
- [ ] ด่านเสมอ + ด่านเงื่อนไขที่เปิดไว้ ผ่านทั้งหมด (มีหลักฐานในการ์ด)
- [ ] ผ่าน UAT ตามเกณฑ์ผ่าน · ตรวจหน้าจริงที่ 375px ถ้า UI เปลี่ยน
- [ ] ขึ้นจริงแล้ว + เฝ้าหลังขึ้นครบ (หรือระบุว่ายังไม่ deploy)
- [ ] release notes · คู่มือผู้ใช้อัป (ถ้าผู้ใช้เห็นความต่าง)
- [ ] ADR ของการตัดสินใจที่มีผลระยะยาว · `docs/HANDOFF.md` อัป · memory อัป (ถ้ามีเรื่องควรจำ)
- [ ] traceability ครบ: story → spec → test → release (`docs/documents.md`)
- [ ] commit ในเครื่อง (Conventional Commits) · push เฉพาะเมื่อสั่ง

## change request (lane `change`)
1. ใครก็ขอได้ · เขียน `templates/change-request.md` แนบการ์ดเดิม (skill `change-request`)
2. intake-analyst + solution-architect ทำ impact analysis: กระทบ requirement / spec / design / เทส / เวลา / ระดับ R / ด่านเงื่อนไข
3. หาขั้นแรกสุดที่ถูกกระทบ → **ย้อนไปขั้นนั้น** · ขั้นหลังจากนั้นทำใหม่ทั้งหมด
4. Owner re-ack scope ใหม่ (ความเห็นลงวันที่) · กระทบเวลา/ขนาด → planning จัดลำดับใหม่
5. ยังไม่ re-ack = ทำต่อตาม scope เดิม ห้ามแอบใส่ของใหม่

## hotfix (lane `hotfix`)
ใช้เมื่อ production เสีย/เสี่ยงเสียตอนนี้ · ไม่ใช่ทางลัดของงานธรรมดา (skill `hotfix`)
- **ย่อได้:** 1–3 เหลือ brief 3–5 บรรทัดในการ์ด · ช่วง UAT สั้นลง (smoke ยังครบ) · release notes สั้น
- **ห้ามย่อ/ห้ามข้าม:** เทส RED ที่จำลองอาการ · GATE-VERIFY · GATE-SEC (เมื่อแตะเส้นทางเสี่ยงสูง R3) · Owner/Ops อนุมัติ deploy (ความเห็นลงวันที่) · เขียนแผนถอยก่อนขึ้น · secret scan + hook ทั้งหมด
- ลำดับ: บรรเทาก่อน (rollback / ปิด flag) ถ้าทำได้ → แก้น้อยสุด → ขึ้น → เฝ้า → **postmortem ภายใน 5 วันทำการ** (skill `postmortem`) → งานแก้ถาวรเข้า backlog เป็น `bug`/`change`
- กติกาอนุมัติ R3 เหมือนเดิมแม้ด่วน (`docs/roles/README.md`)

## WIP limit
- in progress ต่อคน (คนหรือ agent ที่คนนั้นขับ) ≤ 2 การ์ด · ทั้งทีม ≤ จำนวนคน + 1 · hotfix ไม่นับ แต่คนที่รับหยุดงานอื่น
- เกิน limit = ห้ามหยิบใหม่ · ช่วยปิดของที่ค้าง (review / UAT) ก่อน
- กรอกต่อโปรเจกต์: ตัวเลข limit ถ้าต่างจากนี้ (บันทึก ADR)

## งานขนาน
แยกเป็น session/agent เมื่อไม่ชนไฟล์และไม่รอผลกัน · ชนกัน = ทำตามลำดับ · คนเขียนไฟล์เดียวกันมีได้ทีละคน
