# UAT

> เครื่องทดสอบใช้ร่วม · คิวเดียว

UAT = สภาพแวดล้อมที่เหมือน prod ที่สุด ใช้พิสูจน์ว่า SHA นี้ทำงานผ่านระบบจริงก่อนขอ deploy · ตัวขึ้น UAT = agent `uat-release` (หรือ Ops)

## ประกาศ UAT: บอก sha + ช่วงเวลาก่อนสลับ
UAT ใช้ร่วมกัน จึงบอกล่วงหน้าว่าจะขึ้นเวอร์ชันไหน ช่วงใด · โพสต์บนการ์ดก่อนสลับ (ผ่าน `board.mjs post`) ต้องมี:
- SHA เต็มที่จะขึ้น + SHA ปัจจุบันบน UAT
- ช่วงเวลา (เริ่ม–สิ้นสุด) ที่จะครอบครอง UAT
- สิ่งที่ต้องทดสอบ: รายการจาก spec/test plan (`templates/test-plan-l2-uat.md`) · จุดเสี่ยง · จุดที่เปลี่ยน
- ผู้ที่ต้องดู: Frontend (หน้าจริง เมื่อ UI เปลี่ยน) · Owner (ข้อความที่ผู้ใช้เห็น)
- ผลกระทบกับงานอื่นที่ใช้ UAT ร่วมกัน

## ใครถือคิว · คืนเป็นอะไร
- UAT มีคิวเดียว: ผู้ถือคิวเขียน role + การ์ด + ช่วงเวลาไว้ที่ที่เก็บคิว (กรอกต่อโปรเจกต์: ที่เก็บคิว เช่น หัวบอร์ดหรือไฟล์)
- คนอื่นรอ ห้ามสลับ SHA ทับกลางทาง
- เกินเวลา = ขอต่อบนการ์ด ไม่ต่อเอง
- คืนคิวเมื่อ sign-off เสร็จหรือหยุดงาน → โพสต์ว่าคืนแล้ว + UAT อยู่ที่ SHA ไหน
- คืนในสถานะที่รู้ว่าอะไรค้าง: ข้อมูลทดสอบถูกกวาด หรือระบุว่าเหลืออะไร

## ขั้นตอนทดสอบ
1. L2: รันชุดทดสอบผ่านระบบจริงบน UAT ตาม test plan (ผ่านทางเข้าจริง: UI/API) · เก็บผล + log
2. ตรวจหน้าจริง (GATE-UI เมื่อ UI เปลี่ยน) ที่ 375px ทั้งธีมสว่างและมืด (Frontend / `qa-engineer`) · ตรวจ overflow, ข้อความตัด, ปุ่มกดได้, สถานะ error/ว่าง/โหลด
3. GATE-A11Y (ถ้าเปิด): WCAG 2.2 AA — คีย์บอร์ดครบ · focus เห็น · contrast · label/alt · เป้าแตะ ≥ 24px (แนะนำ 44px) · reflow ที่ 320 CSS px
4. GATE-PERF (ถ้าเปิด): วัดตามงบที่กำหนดตอน intake ที่ปริมาณข้อมูลใกล้จริง
5. ตรวจเทียบ scope: ทุก acceptance criteria ในสเปกมีหลักฐาน · ไม่มีของนอกสโคป
6. Owner ดูข้อความที่ผู้ใช้เห็น (ถ้ามี)

## Sign-off
เขียนบนการ์ด (ลงวันที่) ต้องมี: SHA ที่ทดสอบ · ผล L2 (ผ่าน/ไม่ผ่าน + ลิงก์หลักฐาน) · ผล UI/A11Y/PERF ถ้าเปิด · ปัญหาที่เหลือ + ใครรับ · ผู้ sign-off (role)
- R3: ต้องมีคนที่สอง · ทีมคนเดียว = Owner บันทึกรับความเสี่ยงบนการ์ด ซึ่งอ่อนกว่า (`docs/roles/README.md`)
- SHA เปลี่ยนหลัง sign-off = UAT ใหม่ ไม่ใช้ sign-off เก่า
- ไม่ผ่าน → กลับไปแก้ที่ stage ที่เกี่ยวข้อง (bug → เทส RED ก่อน)

## บัญชีทดสอบ (ไม่มีรหัสในไฟล์ · ที่เก็บรหัส)
- บัญชีแยกตาม role (ผู้ใช้ทั่วไป · admin · ผู้อนุมัติ ฯลฯ) ใช้เฉพาะ UAT
- รหัสผ่าน/โทเค็นไม่อยู่ใน git, การ์ด, log หรือแชต · เก็บใน secret manager / password manager ของทีม (กรอกต่อโปรเจกต์: ที่เก็บ + ใครเข้าถึงได้)
- หมุนรหัสเมื่อคนออก/ทีมเปลี่ยน · รหัส UAT ห้ามซ้ำกับ prod

## ข้อมูลทดสอบ (สร้างผ่านทางเข้าจริง · เก็บกวาด)
- ห้ามใช้ข้อมูลส่วนบุคคลจริง: ใช้ข้อมูลสังเคราะห์ (ชื่อ/เบอร์/อีเมลปลอม โดเมน `example.com`) · ถ้าจำเป็นต้องใช้ข้อมูลจาก prod ต้อง anonymize/mask ก่อนและผ่าน GATE-PRIVACY
- สร้างผ่านทางเข้าจริง (UI/API) ไม่ insert ตรง DB เพื่อให้ผ่าน validation/สิทธิ์จริง · ติดป้ายข้อมูลทดสอบ (prefix/tag) ให้กวาดได้
- เก็บกวาดหลังจบ หรือบันทึกว่าเหลืออะไร · seed data ชุดมาตรฐานอยู่ใน repo (ไม่มี PII)
- การส่งออกนอกระบบ (อีเมล/SMS/บริการภายนอก) ต้องชี้ sandbox หรือที่ดักไว้ ไม่ส่งถึงคนจริง

## agent ฝั่ง UAT ห้ามแตะ prod
- `uat-release` ไม่มี credential/เครือข่ายไปยัง prod · config UAT ชี้ UAT เท่านั้น
- ต้องการอ่าน prod = ขออนุมัติอ่านข้อมูลจริงก่อน แล้ว `prod-reader` จึงรัน (ดู `docs/db-scripts.md`)
- เจอ config ที่ชี้ prod ใน UAT = หยุด รายงานบนการ์ด
