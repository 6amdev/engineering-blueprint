# design — ออกแบบก่อนโค้ด

> ขั้น 3

## เมื่อไหร่ใช้
หลัง spec ได้รับ ack · ข้ามได้เฉพาะ R1 ที่เปลี่ยนเล็กและเป็น pattern เดิม (ระบุเหตุผลบนการ์ด) · lane `chore`/`bug` ใช้เมื่อแก้แล้วเปลี่ยนโครงสร้าง

## input
- spec + test inventory · โค้ด/ADR เดิมที่เกี่ยว · ข้อจำกัด non-functional (SLO · ปริมาณ · ความปลอดภัย) · stack ที่ตัดสินแล้ว (`docs/stack-decisions.md` · เกณฑ์ `docs/stack.md`)

## ขั้นตอน
1. **อ่านของเดิมก่อน**: ADR ใน `docs/decisions/` · pattern ที่ repo ใช้อยู่ · ตอบได้ว่ามีของให้ reuse ไหม
2. **ทางเลือก ≥ 2** (รวม "ไม่ทำ/ทำน้อยสุด") · ต่อข้อ: ข้อดี · ข้อเสีย · ต้นทุน · ความเสี่ยง · ย้อนกลับยากแค่ไหน · ประเมินตามคุณภาพ ISO/IEC 25010 ที่เกี่ยว (ความปลอดภัย · ประสิทธิภาพ · บำรุงรักษา · ความเชื่อถือได้)
3. **เลือก 1 ทาง** + เหตุผล (คนไม่แน่ใจ → ทำตัวอย่างหรือของทดลองเล็ก ๆ ให้เทียบ) · ตรวจกับหลัก 12-Factor (config ใน env · stateless · log เป็น stream) ว่าไม่ขัด
4. **ADR** (รูปแบบ Nygard/MADR): บริบท · ทางเลือก · คำตัดสิน · ผลที่ตามมา · สถานะ · วันที่ → `docs/decisions/NNNN-slug.md`
5. **C4**: ทำระดับ context/container เมื่อเพิ่มส่วนใหม่หรือเปลี่ยนการเชื่อมต่อ · component เฉพาะเมื่อซับซ้อน · เก็บเป็น text (Mermaid/PlantUML) ใน `docs/`
6. **ข้อมูล/ความเสี่ยง**: โครงข้อมูลที่เปลี่ยน · migration ย้อนได้ไหม · ค่าลับอยู่ไหน · PII อะไร (→ เปิด GATE-PRIVACY) · ต้องใช้ dependency ใหม่ไหม (→ GATE-DEPS) · เส้นทางที่ต้อง perf (→ GATE-PERF)
7. **design brief 5–8 บรรทัด** จาก `templates/design-brief.md`: ทำอะไร · ที่ไหน · ทำอย่างไร · ไม่ทำอะไร · เทสอะไร · rollback
8. ส่ง **lead-reviewer** (และ challenger หากเสี่ยงสูง) รีวิว → แก้ → ยื่น owner-reviewer
9. **หยุดรอคำว่า "go"** · บันทึกบนการ์ด (role · วัน · sha ของ brief) · ยังไม่ได้ go = ห้ามเขียนโค้ด

## output
- ADR ใน `docs/decisions/` · design brief จาก `templates/design-brief.md` ใน `docs/specs/` (ลิงก์จากการ์ด) · แผนภาพ C4 (ถ้ามี)

## agents
solution-architect (ร่าง) · challenger (ตรวจค้าน R3) · lead-reviewer (รีวิว) · approval-rehearsal (ซ้อมคำถามก่อนขอ "go")

## gates
GATE-DESIGN: ผ่านรีวิว + owner-reviewer ให้ "go" · R3 ต้องมีผู้อนุมัติคนที่สอง หรือในทีมคนเดียว owner บันทึกการรับความเสี่ยง

## หยุดถาม owner เมื่อ
- ทางเลือกที่เปลี่ยนพฤติกรรมธุรกิจ · เส้นทางเสี่ยงสูง · ต้นทุน/ผู้ให้บริการใหม่ · ข้อความถึงผู้ใช้ · รูปแบบ: คำถาม · ก/ข · แนะนำ 1 + เหตุผล · สิ่งที่บล็อก

## checklist done
- [ ] ทางเลือก ≥ 2 พร้อมข้อดีข้อเสีย · ADR เขียนแล้ว
- [ ] C4 อัป (ถ้าโครงสร้างเปลี่ยน) · conditional gates ที่ต้องเปิดระบุแล้ว
- [ ] design brief 5–8 บรรทัด · รีวิวผ่าน
- [ ] "go" บันทึกบนการ์ด
