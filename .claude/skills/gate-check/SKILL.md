# gate-check — ไล่ด่านก่อนส่งต่อ

> นิยามด่านเต็ม: `docs/gates.md`

## เมื่อไหร่ใช้
ก่อนขอ review · ก่อนขึ้น UAT · ก่อนยื่น deploy request · หลังแก้ตามรีวิวทุกรอบ (รันใหม่ที่ sha ล่าสุด)

## input
- การ์ด · sha ปัจจุบัน · รายการ conditional gates ที่เปิดไว้ตอน intake (ดูหัวข้อ "ด่านที่เปิด" ใน brief) · lane + ระดับ R

## ขั้นตอน
1. ยืนยัน sha ที่จะตรวจ · ผลของ sha เก่านับได้ต่อเมื่อตรวจ diff ถึง sha ปัจจุบันแล้ว (กติกา `docs/gates.md`)
2. **ด่านประจำ (GATE-UI เฉพาะเมื่อ UI เปลี่ยน · นอกนั้นรันทุกงาน ยกเว้นที่ lane `hotfix` ย่อได้ตาม `docs/workflow.md`):**
   - **GATE-VERIFY** (test-engineer): หลักฐานเทสที่ไม่ผ่านก่อนแก้ · เทสใหม่ผ่าน · ชุดเทสเต็ม (คำสั่งโปรเจกต์หรือผล CI) ไม่มีเทสล้มเพิ่มจาก base
   - **GATE-SEC** (security-engineer): R1 checklist พื้นฐาน · R2 ASVS L1 · R3 ASVS L2 (skill `security-review`) · hotfix บังคับเมื่อแตะเส้นทางเสี่ยงสูง
   - **GATE-REGRESSION** (regression-tester): ของเดิมที่เกี่ยวยังทำงาน · สัญญา (API/ข้อมูล) ไม่พัง
   - **GATE-UI** (qa-engineer): เมื่อ UI เปลี่ยน — หน้าจริงที่ 375px · ทั้งธีมสว่าง/มืด
   - **code review** (lead-reviewer / คน): skill `code-review`
3. **ด่านเงื่อนไข (รันเฉพาะที่เปิดไว้ — เปิดตอน intake):**
   - **GATE-PERF** (qa-engineer): งบ latency/ปริมาณ · load test เมื่อมีข้อมูลหนัก/query หนัก
   - **GATE-A11Y** (qa-engineer): WCAG 2.2 AA เมื่อมี UI ผู้ใช้
   - **GATE-PRIVACY** (security-engineer): data inventory · วัตถุประสงค์ · retention · สิทธิ์เข้าถึง · PDPA/GDPR
   - **GATE-DEPS** (security-engineer): ช่องโหว่ที่รู้ (SCA) + ความเข้ากันของ licence สำหรับ dependency ใหม่/อัป
   - **GATE-OBS** (runbook-rehearsal/ops): log · metrics · alert · dashboard · SLO · runbook — ก่อนขึ้น prod ครั้งแรก/เส้นทางสำคัญเปลี่ยน
4. ถ้าระหว่างงานพบว่าแตะเรื่องที่ยังไม่ได้เปิดด่าน (เช่น เพิ่ม dependency, เก็บ PII) → **เปิดด่านเพิ่มบนการ์ด** แล้วรัน · ห้ามปล่อยผ่าน
5. ทำตารางสรุป: ด่าน · ผู้ตรวจ · sha · ผ่าน/ไม่ผ่าน/ไม่เกี่ยว (ระบุเหตุผล) · หลักฐาน (`file:line@sha` · path สคริปต์ + sha256 + บรรทัดผล · log + ช่วงเวลา) · ยังไม่ได้ตรวจ = เขียนตรง ๆ
6. **ด่านไม่ผ่าน = หยุด** แก้ที่ต้นเหตุแล้วรันด่านนั้น (และด่านที่ได้รับผลกระทบ) ใหม่ · ห้ามอ้อม ห้ามส่งให้ session อื่นอ้อมด่าน · hook/สคริปต์ปฏิเสธ = หยุดถาม
7. บันทึกทุกผลด้วย `node scripts/gate.mjs add …` แล้วรัน `gate.mjs check <card> --stage uat` · FAIL = หยุด แก้ต้นเหตุ ไม่แก้ไฟล์ด่านให้ผ่าน
8. ผ่านครบ → โพสต์สรุปผ่าน skill `post` · ไปขั้นถัดไป

## output
- ตารางผลด่านบนการ์ด (หรือ `docs/gates/<card>.md`) · ใช้ `templates/card-post.md` เมื่อโพสต์

## agents
เจ้าของด่านตามข้อ 2–3 · lead-reviewer รวมผล

## gates
skill นี้รวมผลด่านประจำ + ด่านเงื่อนไขที่เปิด · "ไม่เกี่ยว" ต้องมีเหตุผลหนึ่งบรรทัด

## หยุดถาม owner เมื่อ
- ด่านไม่ผ่านและต้องเลือกระหว่างแก้ขอบเขต/เลื่อน/ยอมรับความเสี่ยง (R3: owner บันทึกการรับความเสี่ยงลงวันบนการ์ด · ใช้ไม่ได้กับข้อที่ `docs/gates.md` ห้ามผ่านแบบมีเงื่อนไข) · ไม่แน่ใจว่าควรเปิดด่านเงื่อนไขไหน

## checklist done
- [ ] ทุกผลอ้าง sha ปัจจุบัน หรือ sha ที่ผ่าน + diff ที่ตรวจแล้ว
- [ ] ด่านประจำครบตาม lane · ด่านเงื่อนไขที่เปิดครบ
- [ ] ทุก "ไม่เกี่ยว" มีเหตุผล · ทุก "ผ่าน" มีหลักฐาน
- [ ] ด่านที่ไม่ผ่านแก้และรันใหม่แล้ว · ไม่มีการอ้อม
